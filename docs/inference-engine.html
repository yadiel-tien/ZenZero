摘　要

推理引擎把一批棋盘张量映射为 (policy, value)。设计围绕三条硬约束：全部进程内（无 socket、无序列化）、 调用方逐局面提交（批量 API 只是语法糖，凑批始终是引擎的职责）、一个模型实例绑定一份权重与表示版本。 本文给出前向成本模型及其导出的自适应凑批策略（第 5 节）、请求侧镜像增强的等价性说明（第 6 节）、 多引擎并存下的设备一致性协议（第 7 节），并以实测验证 s 网络的成本模型（10 月末批上限 256 时代测点，现上限已提至 2048） 的理论上限、线上稳定于 6 万+（第 11 节）。

1　职责与三条设计约束

引擎做四件事：收批（把散到即到的单局面攒成 batch）、打包（张量化并校验）、 前向（一次网络计算）、投递（把结果送回各请求句柄）。三条约束决定怎么做：

  1. 零拷贝、零协议。训练、对战、评估与引擎同进程，MCTS 与引擎之间只有一个 queue.Queue；ServerHub 是进程内的引擎登记簿，不是网络组件；跨机器只有浏览器走 HTTP。
  2. 一手一请求，攒批归引擎。调用方可以只提交单个局面（批量提交也存在，§10）， 要不要等、等多久、凑多大由引擎按实时负载决定（第 5 节）。这样 §3 篇流水线的 "发一条补一条"才写得直白。
  3. 引擎三身份：架构、表示版本、神经网络。权重文件里存着完整 config；引擎加载时读出 arch / feature_version / profile，此后一切——特征转换的面数校验（§2 篇 §6）、 命名、线程名、面板展示——以这三者为准。全局配置只是缺省值，不是真相（7.1 节）。

3　成本模型：一切策略的地基

s 网络（§6 篇 4.2 神经网络表）在 RTX 5090 D 上扫批实测，线性拟合良好（fp16 autocast，含 H2D）：

tfwd(b) ≈ t0 + κ·b 　　,　　t0 ≈ 1.21 ms，κ ≈ 4.5 µs

由式 (1)，吞吐随批单调升、渐近饱和于 1/κ；固定开销占比随批稀释。两个口径值：

ρ(32) ≈ 2.4 万/秒　≪　ρ(256) ≈ 10.8 万/秒　<　ρ(512) ≈ 14.4 万/秒

3.1　两个被实测否决的优化（负结果也要记）

  • pin_memory（锁页内存）：预期加速主机→设备拷贝，实测批 256 时整体反而更慢 （锁页的分配/同步开销 > 拷贝收益），移除；
  • "TCP 慢启动"式批目标爬坡：批目标从 1 起翻倍、超时就砍半。流水线负载下请求成批到达， 爬坡永远追不上真实批，删除，改为第 5 节的贪心 + 自适应窗口。

4　流水结构：四段，每段一条线程

5　凑批策略：等待有界、随负载自适应

collect 循环（伪码，与代码逐行对应）：

loop:
    q_pend ← 各级队列积压
    delay   ← 1e−4 + 1e−3 · q_pend                # 空闲探测；有活时 get 立即返回
    requests ← [request_queue.get(timeout=delay)]  # 第一条
    while |requests| < B_max:
        try:   requests += request_queue.get(timeout = w(b̂_ema))   # 表 2 的窗口
        except Empty: break
    b̂_ema ← 0.8·b̂_ema + 0.2·|requests| ; 交付 requests
自适应凑批窗口 w(b̂) （代码 _collect_window；"场景"列是工程直觉，不是运行时判据）。
EMA 批 b̂窗口 w典型场景道理
≥ 322 ms满负荷自博弈（G×K 数千常驻）再等 2ms 多攒几十条，换 GPU 一次大发射
≥ 81 ms开局爬坡 / 轮次收尾折中
≥ 30.5 ms残局段仅余数局继续等待难以成批，宜尽快交付
< 30.1 ms人机对战（一手一等）延迟优先，几乎不等
两个正交旋钮。§3 篇的 G×K 决定"有多少料"（供给），本节的 w 决定"愿意花多久凑"（耐心）。 把 K 调大是加供给，把 w 调大是加耐心。2026-11 实测 p90 已打满上限 2048（10 月末均批 215–245 / p90=256 系 B_max=256 时代口径）； 若 window 列持续顶格而均批不涨，说明请求到达速率已足以在零等待下凑满批，此时应调整的是 B_max（历史上从 256→512→2048，式 (2) 还许诺 +33%），而不是继续加 w。

6　镜像增强：请求侧的免费多样性

自博弈请求在提交瞬间（issue()，§3 篇 6.1）被随机施加棋盘的一个对称变换 （象棋左右翻 ×2，五子棋二面体 ×8，记编号 g），返回时结果按 g 还原回原视角：

g ~ Uniform(对称群)　,　(π̃, v̂) ← Engine(g·s)　,　回填使用 (g−1·π̃, v̂)

等价性讨论：不要求网络对对称群等变——变换只作用于"这一次请求"的输入输出对，树里存的永远是原视角。 效果是把同一叶面的评估从"固定一张照片去问"变成"随机抽一张照片去问"，把表示偏差 （若网络略偏爱某侧）平均掉；与仓里的在线增强（§5 篇 5.1）是同一家族的两半 （仓管"训练时多视角"，引擎管"推理时多视角"）。人机对战与评估默认关闭此开关（is_self_play=False）。

7　设备一致性：多模型并存不出事

7.1　输入跟随本模型，而非全局配置

前向张量永远搬到本引擎参数所在设备（_model_device()）。历史事故：另一模型加载失败 触发全局配置降级 CPU，而本引擎权重仍驻留 GPU，"weight is on cuda / input on cpu" 直接崩。配套两道闸：

  • 读写门（_ModelAccess）：forward 持共享锁（w 个 worker 并发读权重安全）； 在线换设备（relocate()，Web 侧栏入口）持独占锁——等在途 forward 排空后搬迁，锁内原子完成。
  • 面数闸：preprocess 校验输入通道数 == 模型出生时的 in_channels，不符抛错。 feature_version 错位的特征是"能跑但全错"，静默比崩溃毒（§2 篇 §6 的教训写进了代码注释）。

此外：混合精度按设备自适应（CUDA fp16 autocast，CPU 关闭）；forward 统一包在 torch.inference_mode()；checkpoint 跨设备通用（加载先落 CPU 再按需迁移， NVIDIA 上训好的权重可直接在 Mac/CPU 上对战）。

9　统计与失败纪律

  • 统计双口径：整轮直方图 Counter（均值 / p50 / p90 按全部批算）与最近 2000 批滑动窗口 （尾部指示、窗口/耗时均值）。曾误以滑动窗口作整轮均值，轮尾的 8–45 小批使头条显示为"均批 16" （实际整轮 237）——两口径分开存、分开报。
  • 线程异常纪律：_spawn() 包住每条线程：异常带堆栈写 logs/crash/， 然后 stop_event.set()。free-threading 下的共享容器纪律：跨线程读写的 deque/Counter 一律持锁、快照后再遍历——曾因打印统计时未加锁遍历，导致投递线程异常终止 （回归测试 test_engine_device_consistency 第 7 项钉住）。
  • 退役顺序：shutdown = 置停 → join 全部线程（每条超时 5s，卡驱动时告警放弃）→ 最后释放权重。顺序反了会炸正在前向的线程（'NoneType' has no attribute 'parameters'（故障与修复均已回归覆盖）。

10.1　调用方（services/inference/client.py）

函数语义
