0　这个 env 是什么

象棋环境是 ZenZero 里 AlphaZero 闭环的物理层：MCTS 只向它要三样东西——get_valid_actions（能走什么）、 virtual_step（走完什么样）、check_winner / game_over（走完后分胜负没有）； 训练采样额外要 convert_to_network（盘面变照片）。它同时是对局规则的单一事实源： 人机对战、selfplay、竞技场、Piskvork、Web 后端全部走同一份判定。

表示版本 2（2026-10-27）两项升级： ①规则从"吃王制"改为官方合法着法制（送将非法，将死/困毙统一判负）； ②棋盘表示从 20 面（棋子+差分+时钟）重排为 26 面清洁布局（last-move / 被将 / 重复 / 时钟 / 兵力 / 将位）。 旧模型（如 checkpoint_498）通过版本感知转换继续原样工作，见 §6。

1　state：(7, 10, 9) 的 int32 张量

环境的唯一盘面真相。行 0 在顶部（黑方底线），行 9 在底部（红方底线）；值：-1 空位，0~6 红子，7~13 黑子。

通道内容更新方式
state[0]当前盘面（唯一"现在"）virtual_step：落子后先做 [1:6]=[0:5] 历史平移，再执行移动——所以层[1] = 上一步之前的盘，依此类推。6 层历史窗口是 last-move 面和窗口重复面的信息来源，树内（搜索路径）与对局天然同构。
state[1..5]最近 5 步的历史盘
state[6]未吃子步数（broadcast 到 10×9）不吃子 +1，吃子归零。判和阈值见 DRAW_NO_CAPTURE_PLIES = 120。

术语·手（ply）：任一方走一步算 1 手；一回合 = 2 手；env.steps 按手计数（代码参数名保留 ply，中文行文说"手"）。注意：state 里没有轮走方、没有全对局重复计数——轮走方是环境/树节点的属性；全对局历史在 RuleContext（不进 state，开局库 npz 因此跨版本兼容）。

2　视角归一化（红黑对称编码）

网络永远只看一种"照片"：当前行棋方永远在下方、永远是 0~6 号子。由 convert_to_network 完成三步：

① 几何翻转：np.flip(state, axis=(1,2))（180°，当 current_player == 1）
黑视角 = 把棋盘转半圈，黑子来到下方
↓
② 子力重新编号：ID_SWAP_MAP（黑子 7~13 ⇄ 0~6）
"行棋方视角"——自己人永远是 0~6
↓
③ 出网后换回：switch_side_policy() = 左右+上下两次动作镜像
网络的 2086 维 policy 翻回真实坐标，MCTS 才接得上
为什么必须换回来：策略头的输出下标语义绑定在动作编码（全局坐标）上，而照片坐标系已被翻转。 换号只在"照片"这一层发生——盘面 state、动作表、树节点永远保持红方视角的全局坐标。任何新增特征面都必须遵守"在翻转后的视角里仍然自洽" （26 面全部满足：广播面天然不变；单格面随棋盘一起翻转）。这正是增强/镜像体系能全局通用的前提。

3　动作编码：2086 = 几何可达的 (from, to) 对

动作是静态、全局、冻结的 ABI（棋盘表示可以开新表示版本，动作编码不行——它被 Cython 表、JS 引擎、policy 语义、镜像表四方引用）。构造见 init_class_dicts()：

区间数量含义
0 ~ 15291530直线走法：每格 17 个（同列 9 个 + 同行 8 个），按格序 r·9+c 排布
1530 ~ 154516士的宫对角
1546 ~ 157732象的田字（含双方半场）
1578 ~ 2085508马的日字（板内全部跳点）

关键理解：编码只枚举"几何上某子力能到达"的格对，不区分是谁走。车、炮、兵共用直线段——合法性（哪个格上真有你的子、蹩腿、炮架、送将）全部由 get_valid_actions 在运行时决定。 因此动作空间永不随规则/表示变化，policy 向量的 2086 维语义跨版本 稳定。

action ←→ move : (r, c, tr, tc)
查表加速: np_move2action[r,c,tr,tc] = action   # C 端索引 r·810 + c·90 + tr·9 + tc
mirror_lr_actions / mirror_ud_actions : 2086 维置换表，用于数据增强与 policy 换边

4　规则引擎（版本 2）：合法着法制

4.1 一次判定解决三件旧事

版本 1 是"吃王制"：送将合法、靠下回合吃掉老将分胜负；连将判负用 6 张历史盘的 ABAB 图案匹配 hack。 版本 2 改为官方规则：

合法着法 = 伪合法着法 − 走完使己方老将被攻击的着法   # R2 过滤，get_valid_actions 内完成

这一个减法自动带来：飞将（照面 = 被敌方帅射线攻击，无需特判）、牵制子不可动、 将死/困毙统一表达（轮走方合法着法集为空即负——象棋里困毙本就判负）、 搜索树少掉约 10~20% 的送将废节点、且不再需要"等老将真被吃"的慢一拍终局。

4.2 game_over：终局裁决的唯一入口

game_over(state, player_just_moved, action, ctx=None, valid_actions_next=None) → GameResult（相对走子方：1胜/0平/−1负/2未终）按优先级：

#条件判定层级
0盘面缺老将缺方负（防御兜底R2 下正常对局不可能出现）树内+对局
1轮走方合法着法为空走子方胜（将死/困毙合一）树内+对局
2未吃子计数 ≥ 120和树内+对局
3双方均无进攻子（车马炮兵）和树内+对局
4同局面(盘面+轮走方)第 3 次出现，且每次都被将军 + 走子方正连续不停照将（≥3 手，一将一闲不罚） + 着法循环不变（两次间隔相等，且相邻两圈着法序列逐一相同——等间隔只是重逢，着法复读才是循环）将军方（=走子方）判负 —— 长将仅对局（需 ctx）
5同局面第 3 次出现，但非循环长将（含"都被将却不等间隔"的散见重复）和 —— 三次重复仅对局（需 ctx）
树内与对局的判定分层是有意设计。MCTS 叶子走到的"重复"是假设着法，不构成对局事实， 所以树内（ctx=None）只做位置级判定（1~3）；三次重复/长将由 env.step 在对局级裁决。 网络则通过 26 面中的窗口重复面（19/20）感知"最近走过重复路"——这是树内/对局分布一致的信号面，判罚本体不在特征里。

4.3 RuleContext：对局过程状态的单一事实源

pos 值格式 [count, chk_red, chk_black, t_prev2, t_prev1]，配一段真实长将轨迹（黑将在 (0,4)/(0,3) 躲红车照将，盯"黑将(0,4)+红车(9,4)+轮黑"这一局面）：

第 1 手  首次出现    [1, 0, 1, 1, 1]        两个时点槽都填手数 1
第 5 手  第 2 次出现   [2, 0, 2, 1, 5]        滑窗: 上上次=1, 上次=5
第 9 手  第 3 次出现   判定(先): total=2+1=3 ✓; checks=2+1=3==total ✓(全被将);
                     9-5 == 5-1 ✓(等间隔循环) → 红长将判负; 再登记(后): [3, 0, 3, 5, 9]

第三个条件的必要性（由评审对话发现）：同一局面完全可能由不同路径周期性重逢——黑将先绕左圈再绕右圈，红车步步照将、局面次次带将、间隔桩桩相等，但两圈的着法序列不同，按官方"着法循环不变"的标准并不成立。为此账本再记一条全局着法流水 move_log，loop_ok() 核查最近 d 手与再之前 d 手逐一相同（seq[-d:] == seq[-2d:-d]）才算复读循环；数据不足时宽松放行（只少罚、不误罚）。回归用例 test_equal_interval_different_moves_not_loop：绕左圈+绕右圈 → 判和；test_perpetual_check_lose：真复读 → 第 9 手判负；test_yijiangyixian_not_punished：一将一闲 → 不罚（三用例 11-05 经对局探针复核语义无误）。

账本之外 RuleContext 还维护 run[红/黑]＝各方当前的连续将军手数（将军 +1，走不将军的着清零）——长将判负要求走子方 run+1 ≥ 3，这正是"连续不停照将"的工程化：一将一闲交替的 run 永远在 0/1 之间摆动，逃过判负。

规则出处（2026-10-27 核对）：长将定义"走子连续不停照将而形成循环达三次，首着吃子不计算在内"（维基·长打）；棋例总纲"任何情况下均不允许单方面长将""一方禁止一方允许，禁止方不变判负""一将一闲为允许着法"（中协《象棋竞赛规则》）；裁决时机"同一局面出现第三次即判"取引擎赛口径（皮卡鱼中国象棋程序竞赛规则，人类比赛为"三次提示变着、再犯判负"，selfplay 无裁判故取等价直判）。

chk_red 恒 0 不是浪费：键含轮走方，同一键的"被将者"永远是同一方，两桶各归各账，判定式才能写成一行 checks == total。

成员说明
pos: dict[key, [count, chk_red, chk_black, t_prev2, t_prev1]]键 = 当前盘面字节 + 轮走方（同盘面不同轮走方是两个位置）；值 = 出现次数 + 按轮走方归类的"出现时被将"数 + 最近两次出现的步号（长将要求最后三次等间隔）
登记时序step：先判定、后登记——判定时约定 total = 历史计数 + 1（本次出现）。开局时 register_current_position() 把初始局面计为第 1 次；任何直接改写 env.state 的调用方（开局库/残局库）必须跟一次它
为什么"连续循环"不需要额外窗口吃子严格减少兵力，而键含全部盘面字节——同一键的两次出现之间不可能有吃子（材料单调性），三次出现必然落在同一个 ≤120 步的无吃子段内，天然不存在"隔全局散见累计"。段内再按"最后三次等间隔"确认处于循环着法中才判负，散见重复只判和。另外同一键的所有出现都由对方走出 ⇒ "每次出现都被将" 自动等价 "同一方在反复将军"，无需走法级图案匹配
关于循环的数学保证：周期 k 步的循环最多再走 ~3k 步必触发三次重复；即便双方不断变着，120 步时钟兜底。 所有循环的 value 都可在有限深度内结算——这正是搜索不震荡的前提。长捉/一将一捉等待判细则明确不做（复杂度悬崖）， 其余重复一律判和；selfplay 日志会按终止原因统计（将死/困毙/和因分类），数据异常再升级规则。

4.3.1 为什么"巡回照将"（局面不重复）不判长将

规则里的长将判负，本质是重复局面的裁决规则：只有同一局面第三次出现（待判局面）才有判罚对象——"循环不变着、着着照将"。局面每步都在变（车换路线、将换方向）意味着被将方每一步都有不同的活路，棋局仍在真实进行，罚它没有规则依据；这类线自然滑向 120 手时钟判和，将军方占不到便宜。 而实战中真正困死人的长将，在"将只有 8 个逃格 × 照将位置被几何锁死"下几乎必然在几手内形成循环——3 次 + 全带将 + 等间隔，恰好就是圈住它的那张网。 不要加"连续将军计数"式变体：那会误伤合法连将杀（每步都将军的攻杀组合正是棋的灵魂），且网络已被面 18/19/20 喂了感知信号，时钟就是这类线的自然上限。

4.4 Python ⇄ Cython 双实现

热路径全在 C：get_valid_actions（伪合法生成 + tmp 盘 make/test 送将过滤）、is_check（王位直接攻击扫描）。 king_attacked 在两侧互为镜像实现（注释互相锚定）：改任何一侧必须跑 tests/test_chess_rules.py 的 2000 局面随机对拍。 无 C 扩展环境自动落回 Python 版（慢但同语义）。初局 44 个合法着法与象棋已知值一致，是过滤正确性的天然交叉验证。

设计三原则（P1 一面一事实 / P2 规则事实必须显式 / P3 别用卷积查数据库），每面 10×9，float32，当前视角：

0–13 棋子 14/15 上一步 from·to 16/17 上上步 from·to 18 被将军 19 窗口重复 20 重复在即 21 吃子时钟 22/23 兵力 24/25 将位
#面内容来源为什么值得一面
0~13棋子one-hot；0~6 己方、7~13 对方（视角归一后）盘面场景本身

数据增强与镜像

  • 训练增强：augment_data 对 (面张量, policy, v) 做左右镜像（象棋唯一对称操作：上下翻转会交换双方），policy 用 2086 维置换表重排。buffer 写入即增强（×2）。
  • 搜索期随机镜像：selfplay 中每次推理请求前 random_mirror_state 随机翻转盘面、回来后翻转 policy——让同一局面以两种镜像进入网络，等效免费增广（这是网络对 LR 镜像近似等变的正则化来源，未来可升级为一致的同变损失）。
  • 26 面全部兼容通用几何变换：广播面天然不变，单格面/空间面随盘翻转且语义保持。

6　feature_version：模型活在自己的表示版本里

核心纪律：面和模型必须成对出现，永不混喂。 26 面不是 20 面的"超集追加"——14 号通道在 版本 1 是差分面、在 版本 2 是 last-move 起点。 同一通道号承载不同语义，因此通道切片兼容方案被废弃（它会静默喂错，比崩溃毒得多）， 代之以版本感知转换。
身份登记：NetConfig 携带 feature_version（新建模型=当前版本；v1 ckpt 无字段=1）。checkpoint 顶层双写。load_from_checkpoint 恢复到 model.feature_version → engine.feature_version
↓
按版本 生成特征面：convert_to_network(state, player, version)——version=1 走原 20 面代码路径（逐通道与 v1 一致，回归测试钉住），version=2 走 26 面；未知版本 raise
↓
feature_version 跟着引擎走：MCTS 树持 planes_version（建树时传入，节点传播）；AIServer/评估赛/selfplay 一律 planes_version=engine.feature_version。引擎入口校验通道数，不符直接报错（宁可崩、不静默）

由此获得的全局能力（跨版本 共存矩阵）

版本 1 模型（498…）版本 2 模型（499…）
人机对战 / Web / Piskvork✅ 各自布局✅
arena 跨版本 比赛（评估赛守擂！）✅ 双方各吃各的面，同一副棋盘对打

这套机制就是多模型 RFC 的第一块地基：以后 WDL 头、分解 policy、杂交主干、大中小网络，都是"注册表 + 身份字段"的存量扩展，不再需要改动任何一条旧链路。

10　已知边界与待办

  • JS 棋规引擎同步（apps/web/js/env-chess.js）：双人同屏/前端判和仍是旧口径，需按 §4 同步并跑 test/web_parity 对拍。后端对战主链路不受影响。
  • 待判细则族：中协规则的长杀/长捉/一将一杀/一将一捉等禁止着法未实现（亚规只禁长将长捉，我们只实现了长将）——不变作负 vs 我们的判和，差异只在对手是人类时才有体验影响；RuleContext 的 run/时点记录留了扩展位，将来只加 game_over 分支。
  • 树内全对局重复：叶子只带窗口信号面；转置表（规划 E5）落地后可升级为路径级精确判定。
  • 人机对战的服务端判罚：AIServer 链路不持有 RuleContext（浏览器是终局权威）——JS 规则同步完成后此项自动闭合。
  • 开局库 npz：快照为 6 层历史 + 时钟，未做版本标记；L2 语义若再变需重导出（工具待补）。
  • 性能路线原则（项目决策）：代码以 Python 为主，Cython 只保留在"影响很大"的既有热路径（走法生成/判将，实测 30 倍差距）；convert 等微优化收益不足两个数量级的不做 C 化，宁可在 Python 层做 numpy 技巧。
  • 动作方向参数化（版本 3 候选）：90+90 源/目标双头替代 2086 维 FC，省 ~5.7M 参数；对外仍 gather 成 2086 维，ABI 不动。
  • memory 提示：象棋 buffer（300k 条）约 2.8GB 状态 + 2.5GB policy，常驻内存偏高；低配机器先降 buffer_size。
