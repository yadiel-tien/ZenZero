ONE-LINER

ZenZero has exactly one process to keep: python main.py (play + console + docs, 127.0.0.1:5000 by default). Once it is up, the browser gives you the game page, the admin console and these docs; open /admin to start/stop training, watch curves and manage models. Training is one more command on the same box (or launched for you by the console). The three-step quick start below covers 90% of use cases.

0　Three-step quick start

1
Set up the environment (one-off) — Python 3.14t + dependencies, see section 1.
2
Start the service: python main.py (binds to 127.0.0.1:5000 by default; add --host 0.0.0.0 to expose it on the LAN, --port 8080 to change port). Open http://<host>:5000/ in a browser and play.
3
Train a model: open http://<host-IP>:5000/admin → Training tab → review game / network / parameters → click “Start training”; when done, click “Stop after round”. No terminal needed.

1　Installation

One environment, managed with uv (a single dependency list, requirements-backend.txt; the frontend has zero dependencies):

uv venv -p cpython-3.14t .venv                          # free-threading interpreter (fall back to -p 3.14 if unavailable — throughput only)
source .venv/bin/activate
uv pip install -r requirements-backend.txt --extra-index-url https://download.pytorch.org/whl/cu132   # NVIDIA Linux
# other backends: swap the extra-index for rocm6.4 / xpu, or use plain pip (MPS/CPU) — torch is unpinned, pick the wheel for your GPU
  • Cython acceleration (optional, strongly recommended): python scripts/build_cython.py; use --check to only verify. Without the .so files it silently falls back to pure Python (identical correctness, lower speed). Do not run setup.py build_ext --inplace directly — overwriting in place while training runs is blocked by the kernel (ETXTBSY) and can leave a half-new binary; the build script already stages and swaps atomically.
  • Model weights: want strong play without training? Grab .pt files from Releases and drop them into data/ChineseChess/ (the m network); the highest iteration is taken as best. For another network (s/l/m8/mini…) create data/ChineseChess/s/ and put the weights there.

2　Playing

With the service up (step 0.2), the game page opens a match in three picks: game → mode → model. Modes: human vs AI (either colour) · two players, one screen · AI vs AI spectate. Model selection is a two-level cascade: network first (s/m/l/m8/mini/custom), then the checkpoint iteration within that network. Before the game you can set a per-move time limit (30–300 s, default 100 s; a human who exceeds it loses on time, the AI is not clocked). AI modes also offer an “AI settings” popover configuring each AI player separately: simulation count (MCTS depth) and sampling temperature (move randomness, 0 = always strongest).

Phones/tablets on the same network just visit the URL; narrow screens move controls into a bottom drawer. Two-player mode is purely local and works without the AI service.

CaseBehaviour
No models installedTwo-player works; vs-AI/spectate report an empty model list (the error names the drop path)
GPU fully busyNew games fall back to CPU automatically (device chip shows cpu; vs-AI caps at 60 sims/move to stay playable). Once the GPU frees up, switch back in one click from settings — engines migrate online, mid-game
Service restartedThe running vs-AI session expires; start a new game. The frontend transparently re-creates a dead session and replays the position (often seamless)

3　Training

3.1　Recommended path: the console

http://<host-IP>:5000/admin　→　“Training” tab　→　Start training

Every form field is a training knob: game, network (s/m/l/m8/mini/custom), worker threads, games per round, virtual-loss K (adaptive — leave it blank), and optionally batch cap and device. The three goal fields may stay empty (= config defaults): stop-at iteration with graceful wrap-up, sims ramp band, and the promotion win-rate threshold. Watch live curves on the Monitor tab after starting. Three stop levels: Stop after round (recommended — self-play + fit + challenger all finish) · Graceful stop (running games are collected into the buffer, then exit) · Kill now (kill -9, loses the current round's unsaved data).

3.2　Bare command (any terminal outside the service)

python -X gil=0 -m scripts.train_server          # repo config defaults
# full-parameter env form:
ZZ_GAME=ChineseChess ZZ_PROFILE=s ZZ_WORKERS=32 ZZ_GAMES_PER_ROUND=400 \
ZZ_BATCH_LEAVES=64 ZZ_DEVICE=auto python -X gil=0 -m scripts.train_server
  • -X gil=0 is mandatory (the first forward lazily imports triton and would re-enable the GIL; without it the multi-threaded MCTS only pretends to parallelize).
  • Resume is automatic from “latest checkpoint + buffer”: any ckpt in the network's directory means warm start; the very first model is promoted unconditionally (no reigning champion).
  • Representation-epoch changes are handled too: if feature_version mismatches the best model, training starts from a fresh network while the old best keeps the throne (§2 ch. §6).
  • When to stop: the four criteria in §5 ch. section 7 (KL flat 10 generations / value plateau / promotion win-rate mean <54% / cross-generation score rate <60%).

4　Console tour (/admin)

Platform note: the console targets desktop browsers (wheel zoom / drag pan / double-click reset); it is fully phone-adapted too — the top strip collapses to a mini 3×2 table, tabs scroll horizontally, tables scroll, chart cards fall to two columns; one finger pans, two pinch, double-tap resets.

TabWhat it does
ServicesEngine registry (ServerHub), play-server sessions (kick one), GPU memory per process (incl. CUDA-context baseline)
ToolsWeb control for the rest of scripts/: piskvork (Gomocup protocol server, network/model cascaders) / bench (engine batch sweep) / build_cython (safe build) — whitelisted args, live logs, tasks re-adopted after service restart
MonitorSix overview cards (games/min & engine throughput, search efficiency split select/wait, training steps, buffer, validation set, challenger) + eight curves (loss·policy/value, policy KL+entropy, win rate, throughput, hardware); wheel zoom, double-click reset, per-card hover help
ArenaMatchmaking platform: multiple arenas each with its own rating list, roster transfer dialog, smart-pairing / gauntlet / custom duel modes, adaptive table parallelism; live games + rankings/strength ladder/head-to-head matrix

AssetsCheckpoints / buffers (incl. clone) / run dirs; all three tables support checked batch delete (per-item guardrails; best refuses); Set as best (rollback the champion)

6　Choosing a network & config quick sheet

  • Start point & buffer: the training form offers start point (resume / fresh training with monotonic iterations / fork from a given iteration) and buffer. The buffer is a game-level resource (data/<Game>/buffers/<name>/, main + holdout as a pair), not per-network — the dropdown lists existing pools, hover shows details (representation version, capacity/used, which network and iteration produced the latest data), last item creates one. Any network may continue on any pool (cross-representation-version is rejected by the startup gate, §6 ch. 4.3). Want to experiment on an old pool without corrupting it: Assets → buffers → “⧉ Clone” (full copy to an auto-numbered pool; pick the clone in the form; disabled mid-training). A buffer must be chosen — the console offers no “none”; new pools are auto-numbered per game (pool1, pool2…) and can be renamed later. In-place pools inside model dirs remain only for bare-command compatibility.
  • Custom networks: console → Training → Network configs names any size combination (e.g. mini64); after saving it is instantly selectable in the training form, game page and assets. Deleting removes only the name — weights on disk stay (a same-named config picks them back up).
  • Which network?: s (8M) trains fast — one night catches the legacy m (§5 ch. 10.3); m (25M) is the default and holds the old assets; l (30M) is the ceiling experiment; m8/mini/mini2 are custom named configs (profiles.json, per game since today). Pools are shared across networks (same representation version) — warm up a big net by pointing it at a small net's pool.
  • All runtime knobs are environment variables (full table in §6 ch.): ZZ_GAME / ZZ_PROFILE / ZZ_DEVICE / ZZ_WORKERS / ZZ_GAMES_PER_ROUND / ZZ_BATCH_LEAVES / ZZ_MAX_BATCH / ZZ_INFER_WORKERS / ZZ_ADMIN_TOKEN; semantics and defaults in §6 ch. Table 4 — the repo config file is never edited at runtime.
  • Where to read versions: game page “Settings” footer and the console title badge (e.g. v2.3.0 · 9f2c1ab), or python main.py --version; the four version axes (app / representation / network / iteration) are explained in §6 ch. 4.4.
  • Static defaults live in core/utils/config.py (c_puct, temperature schedule, dirichlet noise, thresholds, sims ramp, preset sizes).

7　Troubleshooting

SymptomLook here first
Port already in use at startupUse another --port; or find the old process (training runs as a child managed by the console and never collides with the web port)
UI says “cannot fetch model list”Service not up / no .pt in that network's directory; switch network or iteration in the dropdown
Training starts then stops immediatelyFollow the “● live” tail on the Logs tab (file: logs/train/console.log, appended across runs). Most common: buffer can't fill one batch (auto pre-fill kicks in — just wait); or an explicitly requested device is unavailable (by design; use ZZ_DEVICE=auto)
A console number looks staleRead the card subtitle: “live” follows the heartbeat; “last round/stopped” is a perf record or log heuristic; greyed-out values while no training process runs are normal
Suspect a crashlogs/crash/latest.log (thread-level exceptions with stacks); the red banner at the top of the console points to the same place
GPU training throughput tanksOn Monitor, check GPU utilization and “batch wait”: if another process is on the GPU, stagger runs; if the collection window is pinned but batch stays small, raise ZZ_MAX_BATCH (§4 ch. 5)

8　Tests & acceptance

# full regression (tests/, 13 suites, no external framework, CPU only, ~20 min):
for t in tests/test_*.py; do echo "== $t"; ZZ_DEVICE=cpu .venv/bin/python "$t" || break; done
# single suite: e.g. the 21 chess-rule checks — .venv/bin/python tests/test_chess_rules.py

tests/ ships with the repo: drills/ are measurement tools (model_match cross-generation duels etc.), test_*.py are framework-free self-running regressions.

Each chapter's appendix lists which test covers which conclusion; before touching core/env, deepMcts, the batching window or eviction order, run at least the suites named in that appendix. Afterwards remember python scripts/build_cython.py --check.
