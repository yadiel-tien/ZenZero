ABSTRACT

This chapter is the system-layer reference: it first fixes the terminology (section 1), then gives the process topology and the contracts between the processes (section 2), a guided directory tour (section 3), model management under the "architecture registry + network (profile)" scheme (section 4), and the environment-variable configuration surface (section 5); it closes with the complete contract tables for the two HTTP APIs (sections 6 and 7) and the day-to-day operations handbook (section 9). The engineering principle is a single sentence: all heavy state has one source of truth on disk, and every control path can be driven over HTTP — starting and stopping training, rolling back and selecting models all work through the API, with no terminal access required.

2　Process topology and contracts

Origin of one process family: the training process's TrainServer inherits the inference engine (§4 ch. 10.2), so self-play and fitting share weights and the buffer in one process; the server process, in contrast, grows engines dynamically per session. Hence "play is unavailable while training runs" never happens — the two sets of engine instances are unrelated and share nothing but the checkpoints on disk. The price is that each process holds its own GPU memory, so when many engines are resident, runs must be staggered (section 9 of this chapter, the "when the GPU is taken" row).

4　Model management: architecture registry + networks (profile)

Since 2.1, a "network" (profile) is a named model configuration: beyond the built-ins s/m/l, custom size templates can be defined by name in the console under "Training → Network configs" (stored in data/profiles.json; the name doubles as the data directory, and the game dropdown picks it up; currently in service: m8, mini, mini2). Only the size keys may be overridden (channels / residual blocks / value hidden layer / SE); representation-layer and rule-layer keys are refused by a whitelist — a guard both against slips of the hand and against letting a "network" become "a different game".

The checkpoint file stores config (with the arch name and all size keys), the weights, the optimizer/scheduler state and the training step count. Loading rebuilds the network from the config inside the checkpoint, independently of the current process's network configuration — this is the foundation that makes cross-network games (§5 ch. 10.2 drill) and "pick any iteration on the play page" possible.

  • A network preset may override size keys only (channels / block count / head width); in_channels, n_actions, n_cells and feature_version belong to the rule and representation layers — a preset that tries to override one errors out immediately. Network, game and feature epoch must never overstep into one another.
  • The data directories of different networks under the same game are separate (one ckpt/best_index set each), but the experience pool is shared per game: with matching feature epochs, any network can select the same pool and keep accumulating on it (a reference, not a copy; §5 ch. 5 discusses the quality boundaries of a pool).
  • Engine and directory names: the m network keeps the historical form (ChineseChess_498); the others carry a network prefix (ChineseChess_s_34, §4 ch. 8).

4.3　Experience pool (buffer): game-level naming, provenance metadata and the gate

The official name is experience pool (formerly "store"/buffer). A pool ties to the game only, never per network; the source field in the pool metadata records only the provenance fact "which network's which iteration produced the latest content". Clone protection: a pool is ring-overwrite storage, so retraining gradually overwrites old samples — the Assets page's "experience pool" panel offers a "⧉ Clone" button on every row, copying a pool wholesale into an auto-numbered new pool (management lives on the Assets page; the training form only selects a pool) (a full copy rather than hard links, because save() writes in place; it lands as .tmp- and is renamed into position, so a crash never leaves a half-written pool; cloning is refused while training is in progress), letting experiments run on the clone while the original stays pristine. Two storage forms exist: in-place default@<model> (historical compatibility, zero migration), or named pools under data/<Game>/buffers/<name>/ holding the main pool and the holdout set as a pair; meta.json records the game, the feature epoch, capacity/used, and source={model, iteration} (i.e. "whose latest content this is"). A pool of the same game and same feature epoch may be referenced and shared by any model directly (warming up a big net on a small net's pool = selecting the same pool name, no copying); pools whose feature epochs differ are hard-rejected by the startup gate. Every round's save writes the metadata back automatically; the registry is just a live scan of the directories — no second index is kept.

4.4　Versioning (four version axes + one release line)

Since 2.0.0 the project follows semantic versioning. The single source of truth is core/utils/version.py; the version is displayed on: the play page's settings sidebar, the console title badge (v2.3.0 · git build id), /info and /api/admin/health, the startup banner, and main.py --version. The four version axes have disjoint duties:

AxisExample valueMeaning and when it changes
Application version (semver)2.3.0+9f2c1ab The release version of the whole software; the engine / frontend / console are not numbered separately — one repo, one release, and separate versioning would only manufacture a compatibility matrix. Major = representation/protocol-level breaking changes or a milestone; minor = new features; patch = fixes. Release flow: bump version.py → CHANGELOG entry → git tag vX.Y.Z → push tag → GitHub Release (weight files attached).
Feature epoch (feature_version)1 / 2 The board-plane layout epoch, baked into the checkpoint; it determines the feature conversion and the network's channel count, and is incompatible across epochs (§2 ch. §6).
Network (profile)s / m / l The network configuration (built-in s/m/l ∪ customs in profiles.json); it affects size and data directory only, never compatibility (section 4.2).
Model iteration34 The self-play generation within a network (checkpoint_N.pt), advanced by gatekeeper promotions (§5 ch. 8).

When reporting a problem, include all four values — "application version + feature epoch + network + iteration"; the console's meta row and the Assets page already display them together.

6　Play HTTP API (port 5000)

Conventions: everything is JSON. The state array is the (7,10,9) int32 defined in §2 ch.; the session token pid is issued by setup; 60 s without a heartbeat reclaims the session and releases its engine reference; CORS is wide open, so the frontend can be hosted separately.

Play API contract (implemented in services/inference/play_api.py).
EndpointRequest bodySuccess responseNotes
GET /info—{device, device_note, vram{free,total}}device_note flags whether the system is currently degraded (e.g. the CPU fallback after the GPU was taken)
GET /devices—{current, devices:[{…status}]}Available devices (a probe; carries no occupancy state)
POST /device{device}{device}Migrates all loaded engines live; on failure 400 (unavailable) / 409 (migration failed, rolled back)
POST /models{env_name}{indices, best_index, profile, profiles:{s:…,m:…}}Enumerates across networks; profile = the network with the most recent output (the default one, judged by .pt mtime)
POST /setup{model_id, env_class, profile?, n_sim?, temp?}{pid, model_id, profile, device, device_note}Starts a game. model_id=0 → the latest in that network; n_sim defaults by device (lower on CPU to stay playable); temp=0 takes deterministic strong moves
POST /update{pid, array, action, player_to_move}{win_rate}Syncs the board: the AI reuses its search tree (§3 ch. 8.1) and returns the win rate from its own perspective
POST /get_action{pid}{action, win_rate, model_id}The AI plays one move (blocks until the search completes)
POST /reset{pid}{win_rate}New game: the AI's tree and state are wiped
POST /heartbeat{pid}{win_rate}Keeps the session alive

Error conventions: invalid parameters 400; session absent or destroyed 404; engine faults 500 with {error} (including the stack). The browser silently rebuilds a 404'd session and replays the position; other errors surface as a toast; slow responses are guarded by a per-move timeout (the implementation in apps/web/js/api.js is the source of truth for the details).

7　Console HTTP API (/api/admin/)

Read endpoints require no auth (this is an intranet tool); write endpoints check X-ZZ-Token when ZZ_ADMIN_TOKEN is non-empty and answer 401 on a mismatch. The page itself is GET /admin (light/dark themes; follows the system by default, with a manual lock).

GET /arena/list · ranks · state · POST /arena/create · delete · roster · start · stop Backend of the arena (matchmaking platform), core/utils/arena.py: each session keeps its own independent ladder (data/<Game>/rates/<session>/); roster add/remove; batch games in three modes (smart matchmaking / gauntlet / custom duel, adaptive parallel tables); heartbeat at logs/_state/arena.json; the ladder shows Elo / games played / recent form plus a pairwise head-to-head matrix. Note that the win/loss → branch mapping of versus() is pinned by a regression test (on 11-05 an inverted mapping flipped the whole ladder, tests/test_arena_result_mapping.py)

8　Frontend and entry points

8.1　Web frontend (apps/web, build-free)

  • Play page /: three-step game setup (game → mode → cascaded network/iteration picker); the per-move timeout and the per-AI sims/temperature are adjustable before the game (remembered via localStorage); SVG board, Chinese-character notation, dual win-rate bars, a thinking timer, the ⋯ menu (undo / resign), sound effects, mobile-adaptive. The engineering centerpiece is the browser-side rules engine (js/env-chess.js): bit-for-bit alignment with the server's core/env on action encoding, verified by snapshot-level differential testing over random games — otherwise front and back end would diverge on which moves are legal. In human-vs-AI mode the frontend validates moves instantly while the backend focuses on the search computation; neither side waits on the other.
  • Console /admin: six tabs: Monitor / Training / Arena / Assets / Tools / Logs (hash deep-links #monitor/#train/…; at ≤720px the top bar collapses into a mini status strip); hand-drawn Canvas charts (zoom & pan, legends, axis labels); light/dark themes; no external dependencies, no CDN.
