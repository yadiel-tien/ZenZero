ABSTRACT

The training pipeline is AlphaZero's orchestration layer: self-play generates data → a fit produces new weights → a challenger match adjudicates promotion. This chapter reports three engineering decisions and the evidence behind them. First, decoupling rounds from iterations: a fixed number of games per round (400) far larger than the thread count (32), with rolling refill eliminating tail starvation of the form "wave almost over, batches dry up" (§3). Second, policy-target quality over quantity: the simulation budget ramps from 400 to 800 by absolute iteration, because the measured gap between the 200-sim and 800-sim target distributions is 64% of the learnable space (§4 — the 800 simulations per move used in the original [1] follow the same logic). Third, progress metrics built on theory: policy cross-entropy has a hard floor set by the target distribution's own entropy, so "CE is flat" must first be decomposed into KL and entropy before it can be read (§7). The three stop modes and one night's measured report card are recorded in full (§§9–10).

3　Rounds and iterations: rolling refill over 400 games

A round plays nround = 400 games, but the worker pool has only G = 32 threads — games are rolled in with immediate refill: whoever finishes first takes the next game at once, so the pool runs near saturation at any moment. This parameter came from real user feedback: "50 games per round — while the last few games drag on, no big batch assembles and you just sit waiting." Quantitatively, that is two problems:

  • Batch starvation: in a wave of 50 games, the tail leaves only 1–2 games running, in-flight requests across the fleet drop to 1–2, and the engine cannot assemble batches. The fix is exactly this section: games per round ≫ thread count, so the tail is always "dozens of games each on its own" rather than "the whole wave down to two". Measured, the mean tail batch rose from single digits to 12–45 (the K=12 era, 2026-10-27); after the batch cap was raised to 2048, p90 batches now saturate the cap (11-06);
  • Iteration-change variance: promoting on 50 games carries statistical noise that is too large (±7%); 400 games give enough samples, and iterations also come faster.
Opening diversity is not noise; it is a data policy. Each chess game starts 30% from the opening book (≈10 plies in), 40% from the mid/endgame library (≈50 plies in) and 30% from the standard opening — sending search budget to "where the game actually diverges", while naturally easing draws (opening-cycle repetition is one main cause of long draws). If a terminated position ever crept into a library the root node threw an exception (it happened once, costing a whole round's data); library entries are now validated before use (terminated with no legal moves → draw a new game instead; regression-tested in test_graceful_stop / test_admin_tasks).

4　Search budget: the yardstick of policy-target quality

Simulations per move ramp by absolute iteration (not by rounds elapsed since this launch — the old implementation used that, which reset the starting point at every restart, so the ramp never actually engaged):

Nsim(g) = N0 + (Nmax − N0) · min(1, g/gramp) 　,　N0=400，Nmax=800，gramp=50

Why start at 400 rather than "whatever runs"? The MCTS training target πtgt is exactly the visit distribution this tree counts out itself (§3 ch. eq. (3) — the target distribution is what this chapter calls the policy target), and the policy target's own error directly sets the ceiling on what can be learned. Measured on a common batch of mid-game positions (checkpoint_3, each position run once at 200 and once at 800 simulations):

KL( π200 ‖ π800 ) ≈ 0.36　(4 mid-game samples, range 0.27–0.46)　,　H(π200) = 3.04 < H(π800) = 3.50

Section 7 defines KL as a measure of the "learnable space". Put 0.36 in that frame: the whole learnable space in the 200-sim era was about 0.57, and sixty percent of it was noise that would change with a new seed. Doubling the budget is affordable — the cost is halved throughput, and on the throughput base of §10 that is a net gain. The matches in [1] ran 800 simulations per move, identical to this framework's ramp cap — different roads, same destination.

5　Data side: buffer, online augmentation, holdout set

5.1　The ring buffer and "store once, sample many"

The buffer is a fixed-capacity ring array (C = 300k); once full, it discards the oldest entries. The trade-off between two design generations:

  • Old scheme (deprecated): on insert, store all |𝒢| symmetric faces of a sample (×2 for chess, ×8 for Gomoku). Then 1−1/|𝒢| of the buffer is near-duplicate positions, and uniform sampling amplifies their exposure — in effect manufacturing overfitment;
  • Current scheme: store once, sample many. The buffer holds raw samples only; when get_batch() samples, each row independently gets a random g ∈ 𝒢 applied (eq. (3)). The same-size buffer then carries |𝒢|× as many distinct positions, and the n-th time a slot is sampled is still a fresh view.
batch row i = ( gi·xk(i) ,　gi·πk(i) ,　zk(i) ) 　,　k(i) ~ Uniform(buffer) ，gi ~ Uniform(𝒢)

Transform correctness is pinned by bit-exact differential testing: the online transform ≡ the old full augmentation at insert time (test_replay_online_augment).

5.2　Holdout validation set: 2%, partitioned sample-exclusively

Every sample rolls a val_holdout_ratio = 2% die on insert: a hit goes into val_buffer.pkl (capacity max(8000, C/16) = 18,750) and never participates in training; a miss goes into the training buffer. The split is per sample (not per game), so adjacent positions from the same game can land one in the training buffer and one in the holdout set — this is deliberate: position-level holdout measures generalisation to similar positions, which matches this framework's evaluation purpose (overfit watch, KL); measuring "never-before-seen strategic styles" is the job of cross-generation matches (§§8, 10).

5.3　The persistence trio

After each round of self-play and after buffer pre-fill, save() writes an atomic pickle; alongside it goes a .stats.json sidecar (size/capacity/pointer/timestamps) — the console reads the small JSON instead of deserialising a 5 GB buffer. Holdout metrics are written to logs/fit/val_latest.json for the same reason (do not treat a log tail as a database). A failed save only warns and never interrupts — the in-memory buffer remains the source of truth.

6　fit: one round, one lesson

Each round samples the whole buffer P times, for a total of

S = ⌊ P · size(buffer) / B ⌋ ≈ 8 × 300,000 / 2048 = 1171 steps/round

The current default network (resnet_wdl_v1) takes the WDL three-head form: the value target is the one-hot terminal result z ∈ {win, draw, loss}, learned as a three-class cross-entropy — beyond MSE regression on ±1 this gives "draw" an explicit channel, and it also retires the 0.5z+0.5q variance-glue mixture (that mixture was abandoned in early November):

ℒ(θ) = meanB[ CE( z , wθ(x) ) · λv − πtgt⊤ log pθ(x) ] + c‖θ‖² 　(λv=value_loss_weight=0.1, calibrated by gradient share; legacy two-head archs still train compatibly as (z−v)² MSE)

7　Metric methodology: don't mistake the floor for the bottleneck

The policy target is a distribution-fitting problem, and cross-entropy has an irreducible lower bound (Gibbs' inequality; π is the search target, pθ the network output):

CE(θ) = Σa π(a) log π(a)pθ(a) 　=　KL(π ‖ pθ) 　+　 D(π)

D(π) (target entropy) does not depend on θ — even when the model fits seamlessly, CE still equals it. Three cross-sections measured on the holdout set (the ramp of eq. (1) happened to move this floor underneath them):

Decomposition of CE (full holdout set, 15k→18.75k samples; H falls because sims rise and the target turns "sharper" — how much of CE's surface progress is just the floor dropping becomes obvious).

When to call this net converged — four termination criteria (all must hold together): ① KL stops falling for 10 consecutive iterations (measured on same-policy-target cross-sections; see the note on Fig. 2); ② Val/value fluctuation over the last 10 iterations <5% (under the WDL three heads this is CE — not comparable to two-head MSE numbers; use relative cross-sections of the same net); ③ the promotion-match win rate averaging below 54% (new iterations generally fall short of the reigning one); ④ cross-generation match score rate <60%. If ①② are met but ④ still climbs, the bottleneck is capacity — scaling the network beats more training rounds; only when ①②④ hold together does the run touch the capability ceiling of the current representation and search configuration.

8　The challenger match: promotion mechanics

A new model must defeat the reigning champion to take over, guarding against "high score, weak play" regressions where loss falls but chess does not. Up to n=100 games (each side with its own inference-engine instance, 300 sims, K per CONFIG; openings are book lines rotated without replacement plus 4 fixed standard-opening slots — two per colour for the challenger, so no line is replayed and samples burned), with score and verdict:

score rate = W + D/2n 　(draws score 0.5)　;　promote ⟺ score rate > θwin = 0.52

Two early-stop rules eliminate informationless games: cut off as soon as even a clean sweep of the remaining games could not flip the verdict — usually done in 85–96 games, about 50 s. Candidate numbering always takes "largest existing + 1", and a failed candidate's checkpoint is deleted on the spot — so the next candidate reuses the same number, and the "iteration" curve plateaus or even steps back one (measured progression 5,4,4,5,5,6,7,7) — the console shows this faithfully: it is intended semantics, not a defect.

The draw rate once reached 40–50%; after the protocol fix it fell to ~24% (no-replacement book lines + diversified openings, measured 11-05; pathological threefold repetitions largely reduced) — the remaining draws are still a property of xiangqi rules: threefold repetition draws, perpetual check loses (for the checker), and the 120-ply clock (draw after long no-progress) all adjudicate per the official rules (§2 ch. 4.2), but adjudication lacks any material-structure assessment of "draw inevitability" — slowly progressing endgames mostly get dragged into repetition draws or clock draws. Draw samples with z≈0 are not bad data (they teach the model a sense of even positions), but the discrimination of promotion decisions suffers. The improvement path (finer insufficient-material handling, stalemate-rule tuning) belongs to §2 ch.'s rules layer — see its "boundaries & to-dos" there.

The promotion rate is itself a health indicator (the figures below are an old-basis cross-section from 11-05, before the versus win/loss mapping was fixed and the leaderboard cleaned; order of magnitude only): the s net was evaluated 25 times and promoted 14 (56%), with win rates concentrated in 52–63% — a threshold slightly above the half-pawn line makes for "each iteration a small step, direction positive".

9　Stop semantics: three modes and one bottom line

Stop modes (the HTTP interface maps one-to-one to console buttons, §6 ch.; signal semantics in scripts/train_server.py).
ModeSignalBehaviourThis round's data
Finish the round (finish_round, console "stop after round")SIGUSR1②→⑤ run to completion — fit, challenger and perf all finish — then exitcomplete
Graceful stop (interrupt)SIGINTstop dealing games, cancel queued ones; games in progress are collected into the buffer, then save and exit; if called during fit, save the ckpt and skip the challengerall finished games kept
Kill now (kill)SIGKILLhard OS killthe round's unsaved part is lost

Bottom-line discipline (all of it dug out the hard way by drills on 1027–1028, then locked in regression tests):

  • Signal handlers are registered before heavy work. Loading the buffer at startup takes over a minute; during that window a default-action SIGINT would hand the main thread a KeyboardInterrupt and the process would exit with code −2 (there is nothing to save at that point, yet the console shows an abnormal exit code — an easy misdiagnosis).
  • Teardown is bounded. Engine-thread joins take ≤5 s each; total teardown ≤20 s, then os._exit — "data saved, process won't die" was once escalated to SIGKILL by an external supervisor, leaving the state misleading ever after (test_graceful_stop / test_admin_tasks regression).
  • The grace period extends dynamically. Once a graceful stop enters its drain phase the heartbeat carries a stopping flag, and while the runner sees fresh heartbeats it does not escalate SIGINT to SIGKILL (a fixed 150 s grace once killed a slow drain by mistake; drill D reproduced and fixed it: test_drain_keeps_grace).
