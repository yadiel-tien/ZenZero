ABSTRACT

The inference engine maps a batch of board tensors to (policy, value). The design revolves around three hard constraints: everything runs in-process (no sockets, no serialisation); callers submit position by position (the batch API is only syntactic sugar — batching is always the engine's responsibility); one model instance is bound to one weight set and one representation version. This chapter gives the forward cost model and the adaptive batching policy derived from it (§5), the equivalence argument for request-side symmetry augmentation (§6), and the device-consistency protocol under multiple coexisting engines (§7); it also verifies the s-network cost model against measurements (data points from the late-October era of a 256 batch cap, the cap now raised to 2048) — the theoretical ceiling and the production steady state above 60k requests/s (§11).

1　Responsibilities and three design constraints

The engine does four things: collect (gather single positions, arriving one by one, into a batch), pack (tensorise and validate), forward (one network computation), post (hand each result back to its request handle). Three constraints decide how:

  1. Zero-copy, zero-protocol. Training, play, evaluation and the engine share one process; between MCTS and the engine there is only a queue.Queue; ServerHub is an in-process engine registry, not a network component; across machines, only the browser speaks HTTP.
  2. One move, one request; batching is the engine's job. A caller may submit a single position (batch submission also exists, §10); whether to wait, how long and up to what size are decided by the engine from the live load (§5). This is what lets §3 ch.'s pipeline be written as plainly as “send one, refill one”.
  3. Three engine identities: architecture, representation version, network. The weight file stores the complete config; at load time the engine reads out arch / feature_version / profile, and from then on everything — the plane-count check on feature conversion (§2 ch. §6), naming, thread names, panel display — defers to these three. Global configuration is only a set of defaults, not the truth (§7.1).

3　Cost model: the foundation of every policy

Sweeping the s network (§6 ch. 4.2, neural-network table) over batch sizes on an RTX 5090 D fits the linear model well (fp16 autocast, incl. H2D):

tfwd(b) ≈ t0 + κ·b 　　,　　t0 ≈ 1.21 ms, κ ≈ 4.5 µs

By eq. (1), throughput rises monotonically with batch and saturates asymptotically at 1/κ, while the share of fixed overhead dilutes as the batch grows. Two reference points:

ρ(32) ≈ 24k/s　≪　ρ(256) ≈ 108k/s　<　ρ(512) ≈ 144k/s

3.1　Two optimisations vetoed by measurement (negative results get recorded too)

  • pin_memory (page-locked memory): expected to speed up the host→device copy; measured, it made overall throughput at batch 256 slower (the allocation/synchronisation overhead of pinning > the copy gain) — removed;
  • a “TCP slow-start” ramp of the batch target: double the target from 1, halve it on timeout. Under pipelined load requests arrive in batches, so the ramp never catches up with the real batch — deleted in favour of §5's greedy fill plus adaptive window.

5　Batching policy: bounded waiting, load-adaptive

The collect loop (pseudocode, line-for-line against the code):

loop:
    q_pend ← backlog across all queue stages
    delay   ← 1e−4 + 1e−3 · q_pend                # idle probe; get returns at once when there is work
    requests ← [request_queue.get(timeout=delay)]  # first item
    while |requests| < B_max:
        try:   requests += request_queue.get(timeout = w(b̂_ema))   # the window from Table 2
        except Empty: break
    b̂_ema ← 0.8·b̂_ema + 0.2·|requests| ;  deliver requests
Adaptive batching window w(b̂) (code _collect_window; the “scenario” column is engineering intuition, not a runtime predicate).

Two orthogonal knobs. §3 ch.'s G×K decides “how much material there is” (supply); this section's w decides “how long one is willing to spend collecting it” (patience). Raising K adds supply; raising w adds patience. Measured in 2026-11, p90 already saturates the 2048 cap (the end-of-October mean batch 215–245 / p90=256 are figures from the B_max=256 era); if the window column keeps pinning at the cap while the mean batch does not grow, the request arrival rate is already high enough to fill batches with zero waiting — what to adjust then is B_max (historically raised 256→512→2048; eq. (2) still promises +33%), not more w.

6　Symmetry augmentation: free diversity on the request side

A self-play request, at the moment of submission (issue(), §3 ch. 6.1), is randomly put through one symmetry of the board (xiangqi left–right flip ×2, gomoku dihedral group ×8; call the index g); when the result returns, it is mapped back through g to the original view:

g ~ Uniform(symmetry group)　,　(π̃, v̂) ← Engine(g·s)　,　stored and used as (g−1·π̃, v̂)

Equivalence discussion: the network is not required to be equivariant under the symmetry group — the transform acts only on the input–output pair of “this one request”, and what the tree stores is always the original view. The effect is that evaluating the same leaf changes from “ask about one fixed photograph” to “ask about a photograph drawn at random”, averaging out representation bias (if the network slightly favours one side); with the buffer's online augmentation (§5 ch. 5.1) it forms the two halves of one family (the buffer owns “many views in training”, the engine owns “many views at inference”). Human-vs-AI play and evaluation switch this off by default (is_self_play=False).

7　Device consistency: many models coexisting without accidents

7.1　Inputs follow this model, not the global configuration

Forward tensors are always moved onto the device this engine's parameters live on (_model_device()). Historical incident: another model failed to load, the global configuration degraded to CPU, yet this engine's weights still sat on the GPU — “weight is on cuda / input on cpu” crashed on contact. Two gates come as a set:

  • Read/write gate (_ModelAccess): forward holds a shared lock (concurrent weight reads by w workers are safe); an online device move (relocate(), exposed in the Web sidebar) holds an exclusive lock — it waits for in-flight forwards to drain, then migrates, atomically inside the lock.
  • Plane-count gate: preprocess checks that the input channel count equals the model's birth-time in_channels and raises otherwise. Features built under a mismatched feature_version are “runnable but entirely wrong”; silence poisons worse than a crash (the lesson of §2 ch. §6 is written into the code comments).

Beyond that: mixed precision adapts per device (fp16 autocast on CUDA, off on CPU); every forward is wrapped uniformly in torch.inference_mode(); checkpoints are device-portable (loaded to CPU first, migrated as needed — weights trained on NVIDIA play directly on Mac/CPU).

8　Multi-model sharing: ServerHub

engine, loaded_id = hub.get_engine(env_name, model_id, profile)    # model_id=0 → latest of that network
# hit: reference +1, reuse directly; miss: InferenceEngine(index, env, profile) built and start()-ed
# AIServer.shutdown() / session timeout → reference −1 → only at zero: stop threads, release GPU memory

Engines are named and registered by the triple (game, network, index): ChineseChess_498 (the m network keeps the historical format) / ChineseChess_s_34 (the rest carry a network prefix). Thread name, log, panel and statistics all key on the same string — “same-generation models of two networks” are never mistaken for one engine. The two contestants of a promotion match (§5 ch. 8) are exactly two such instances.

9　Statistics and failure discipline

  • Dual scope: a whole-round histogram Counter (mean / p50 / p90 computed over all batches) versus a sliding window of the last 2000 batches (tail indicators, window/latency means). Mistaking the sliding window for the whole-round mean once made the headline read “mean batch 16” because of 8–45 tail batches at the round's end (whole-round actual: 237) — the two scopes are stored and reported separately.
  • Thread-exception discipline: _spawn() wraps every thread: exceptions are written with their stack traces to logs/crash/, then stop_event.set(). Shared-container discipline under free-threading: deques/Counters read and written across threads are always mutated under a lock and iterated only on a snapshot — once, an unlocked iteration while printing statistics terminated the post thread abnormally (pinned by item 7 of the regression suite test_engine_device_consistency).
  • Retirement order: shutdown = set the stop flag → join all threads (5 s timeout each; warn and give up if the driver hangs) → finally release the weights. The reverse order explodes threads caught mid-forward ('NoneType' has no attribute 'parameters'; the fault and its fix are both covered by regression tests).
