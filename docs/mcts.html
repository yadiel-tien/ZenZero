ABSTRACT

This chapter describes the tree-search layer of ZenZero. It faces exactly one engineering contradiction: an AlphaZero-style search performs hundreds of network evaluations per move, while the GPU is only efficient when it receives tens or hundreds of positions at a time. The contradiction is resolved along two orthogonal routes — virtual loss (section 5) keeps the K search lines within a single move from trampling on each other so they submit concurrently; the barrier-free pipeline (section 6) keeps the request stream continuous in time, so that at any moment the engine has enough to assemble a batch. Both preserve semantic consistency with serial search (argued in section 5.3 and covered by the tests in the appendix). Measured search-request throughput rises from 5.8k to 62.9k positions/s (10.8×); under an equal search budget, self-play improves from 6.7 to 95.4 games/min (section 9).

1　Introduction: why search is the bottleneck

In the three-layer structure of the AlphaZero loop [1] (game rules → §2 ch., decision → this chapter, compute → §4 ch.), MCTS (Monte Carlo Tree Search) amplifies “the network's intuition” into “a computed decision”: hundreds to thousands of playouts are run on the current position; each playout descends the tree to an unevaluated leaf, asks the neural network for that leaf's prior policy and position evaluation, and back-propagates the result along the path. The final move is drawn from the visit distribution π (section 7.1).

This loop has two natural properties that together make it the engineering bottleneck:

  • Serial dependence: a playout's descent path depends on the statistics of all previous playouts — in a naive implementation “ask the network → back-propagate → descend again” must run sequentially, and the GPU receives only one position at any instant;
  • High fixed cost: most of the cost of one GPU forward pass is fixed (§4 ch. eq. (1)); a batch holding a single position versus one holding 256 takes less than twice the time, yet the cost amortized per position differs by more than a hundred times.

So the entire chapter can be summed up in one sentence: without changing the search semantics, reschedule “one question at a time” into “many questions in parallel, batched as they arrive.” The instruments are virtual loss (parallelism along space) and the pipeline (continuity along time).

3　PUCT: upper-confidence tree with priors

At each descent step, at node s, the legal action maximizing the following is selected (a UCT variant with an added network-prior term; the form is taken from AlphaZero [1]):

U(s,a) = W(s,a) + cpuct · P(s,a) · N(s) 1 + N(s,a) 　,　a ∈ A(s)

The first term of the numerator is the accumulated return (the larger it is, the more the edge deserves play); the second rewards “prior × not yet sufficiently explored”; the denominator makes the marginal gain of selecting the same edge again decay. An edge never tried (N=0) still gets a chance as long as P is nonzero.

Two implementation details (equivalent to the pseudocode, but worth writing down):
① Common pseudocode writes the argmax object as “mean Q̂ + exploration term”; this implementation folds both terms into a single fraction and does one argmax(child_scores) — expanding Q̂≡W/(1+N) back to the common denominator, the two forms are identical; the payoff is that each node stores only three fixed-length arrays W/N/P, the mean is never maintained on its own, and there is neither division by zero nor a rounding fork.
② The arrays are aligned compactly to A(s) (length 30–60, not the full 2086-action space), so every selection is one short-array scan; action ids are restored through the valid_actions index. Leaf selection is the hottest path, and this step compresses the scoring workload to 1/35–1/70 of the full-action-space footing (2086 ÷ 30–60).

3.1　Leaf evaluation and the terminal short-circuit

Descending to an unexpanded leaf splits into two branches. If the rules have already called the position terminal (checkmate / stalemate / draw / perpetual check / clock, §2 ch.), the terminal reward is taken and back-propagated directly, consuming no network request — this branch is the terminal short-circuit, and its share grows as the game nears the endgame. Otherwise the position is converted to a tensor (§2 ch. §5), submitted to the inference engine (§4 ch.), and −vθ is back-propagated as the leaf return (viewpoint conversion: section 7.3).

4　Quantifying the bottleneck: where batches come from in serial mode

Let G be the number of concurrent self-play games. In the serial implementation each game has at most one outstanding request at any instant, so the expected ceiling of a GPU batch is G; and the alternating “descend—wait” makes requests arrive in bursts, so the batches the engine actually assembles fall far short of G (the first row of Table 3 in section 9 shows exactly this shape). Two measurements give the quantitative basis:

  • Batching cost model (§4 ch. eq. (1): forward time tfwd(b) ≈ 1.21 ms + 4.5 µs·b): at batch 32 each position costs 42 µs, at batch 256 it costs 9.2 µs — a 4.5× throughput difference on the same card;
  • the intermediate barrier batching form (send K → all return → send the next batch) doubles throughput, but during the “wait for all” the thread produces no new requests and the engine queue drains — the measured GPU duty cycle was only 34%. This directly motivated the barrier-free pipeline of section 6.

5　Virtual loss: keeping K lines simultaneously alive

5.1　Mechanism

The first obstacle to concurrency: two lines in the same decision descend along the same statistics and crash into the same leaf. The remedy is to temporarily book a fake entry against the just-selected edge:

N(s,a) ← N(s,a) + ν 　　,　　W(s,a) ← W(s,a) − ν 　　(valid until this edge's result returns)

Both numerator and denominator of eq. (1) are worsened at once, the edge's score plunges, and later selections naturally divert; when the real result returns, the two entries are undone pairwise along the path (_undo_virtual_loss), restoring the true statistics.

5.2　Why W is decremented too (not just N incremented)

If only N were incremented, then whenever the edge's empirical return clearly beats its peers, its decayed score could still be the highest of the lot and the second line would collide all the same. Also decrementing W by ν is equivalent to “booking a fake loss under its name”; even the strongest edge gets pushed down — diversion turns from a probabilistic coincidence into a structural guarantee. The price is that during the fake-entry window the edge's statistics are temporarily distorted, so the undo must be pairwise: any code path in which “the result is lost and the fake entry never returned” would permanently pollute the statistics. In this framework the undo and the return live in the same harvest routine (pseudocode in section 6.1), and test 5.3-① pins the conservation invariant down by regression.

5.3　Semantic equivalence and two invariants

Compared with serial PUCT, virtual loss changes the selection sequence (it spreads out more), not the ledger of each request: every line still fully experiences descend—evaluate—back-propagate; while several lines are in flight they cannot “see” the moves the other has just booked, so under the same random seed the final visit distribution is not bitwise identical to the serial one — an inherent property of parallel tree search, universally accepted in AlphaZero-style implementations. What must hold at all times are two invariants:

  1. Fake-entry conservation: at any moment Σ(undone virtual losses) = requests in flight ≤ K;
  2. The budget is never burned by skips: a selection withdrawn because of a collision must not consume simulation budget (the defect described in 6.2-①).

6　The barrier-free pipeline: one returns, one departs

6.1　Structure

Barrier batching (send K, wait for K) admits no new requests into the queue while waiting, opening a gap in the request supply for batching. run_pipelined() drops the barrier and maintains the invariant “always ≤ K in flight”:

in-flight table inflight ← ∅ ;  budget rem ← n_simulation
while rem > 0 or inflight ≠ ∅:
    while rem > 0 and |inflight| < K:
        (leaf, path) ← select() and book the virtual loss (2)
        if leaf ∈ inflight:          # when the tree is shallow, all K selections may land on one leaf
            undo (2) ; break          # consumes no budget; leave the loop and go harvest (6.2-①)
        if leaf already terminal:     # short-circuit, section 3.1
            undo (2) ; back-fill on the spot ; rem − 1 ; continue
        submit leaf network input → engine request queue
        inflight += request ; rem − 1
    wait for “any one” completion (semaphore permit; raise an explicit error past a 300 s timeout)
    pick any completed request: undo (2) → back-fill real result → inflight − 1

6.2　Two correctness details (each behind a real incident)

  • ① A collision must not burn budget. When the tree is shallow, K selects may all land back on the same unexpanded leaf. The early implementation counted the skip against the simulation budget: 48 simulations were exhausted by “skips”, the call returned before the root had expanded, and the downstream get_pi received an empty distribution and crashed outright. The correct behavior: undo the fake entry, deduct no budget, and yield the refill loop to harvesting; continue once the tree has opened up.
  • ② Harvest via the semaphore, not per-request waits. Each completion releases one permit (§4 ch. RequestLane); after acquire() the main loop finds any completed request in the in-flight table and processes it — avoiding the dead waits of “picking one to wait for”, so out-of-order completion works naturally.
The timeout is a safety net, not decoration. If the engine is half-dead (requests go in, nothing comes back), nothing completing within 300 s throws TimeoutError, so the whole training chain fails explicitly and lands in the log; without it the process hangs silently — on the monitoring dashboard such a failure shows up only as “stalled”, and triage costs dearly; this scenario is covered by a regression on the timeout path.

7　Policy targets, noise and viewpoints

7.1　Visit counts → policy distribution

Both the training target and the move distribution produced by the search use the same mapping (the implementation computes in the log domain — equivalent to power normalization but immune to overflow):

πτ(a) ∝ N(a)1/τ 　(τ > 0)　;　as τ → 0, π degenerates to a point mass on argmaxa N(a)

Training samples take the policy target at τ = 1 (visit-count proportions are “the search's opinion”); over-the-board moves: during the first exploration_steps moves τ = 1 stays constant to encourage exploration, then τ = 0.1, nearly greedy. The window is sized to each game's typical length: xiangqi 30 moves, gomoku 12 (games commonly end within 20–40 moves; a longer window would mean random play for the whole game); config keys tau_decay_rate / exploration_steps (currently 1.0 = a constant segment).

7.2　Dirichlet noise at the root node

P̃ = ε · ξ + (1 − ε) · P 　,　ξ ~ Dir(α) 　,　α = 0.03 × 361 / |A(s)| 　,　ε = 0.25

Added at the root node only, and only during self-play (P in the equation is the prior field written when the root's evaluation lands; the noise simply overwrites it): it keeps a revolving door open for moves the network momentarily disfavours but that are worth testing. Human-vs-AI games and promotion evaluation add none — what is needed there is simply the strongest current move. Scaling α inversely with the number of legal moves is the convention of [1]; ε is the config key dirichlet.

7.3　Viewpoint conventions (the most error-prone line of bookkeeping in the whole framework)

  • value head vθ(s): the side-to-move view (the score belongs to whoever is to move);
  • edge accumulator W(s,a): the view of the player moving into the child (= the parent-side player who played the move) — hence an evaluation lands with Rt = −vθ, and the back-propagation loop's “negate at this level, negate again level by level” alternates the two players' viewpoints naturally;
  • q in training samples: −Wroot/Nroot taken at the root position, i.e., converted back to a “side-to-move” search estimate.

A model with the direction flipped reliably learns to “play for the opponent”, while the training-loss curves look perfectly normal — that is the frightening part. The seven checks in tests/test_mcts_reward_sign.py verify this viewpoint sign chain level by level along the path (appendix).

9.1　Measurement methodology

  • The throughput denominator counts positions (a forward pass with B positions in the batch credits B), aggregated from the statistics line the engine prints every thousand requests (§4 ch. section 9), not a client-side estimate; batch statistics are additionally kept as a whole-run histogram — the panel headline uses the whole-run mean, and the sliding window serves only as a tail indicator; using the sliding window as the run mean once mis-reported 245 as 16 (now covered by a regression test; “whole-run 237” in §4 ch. is the same data read on the whole-run basis).
  • The thread count has a measured inflection point: 24–32 threads ≈ 47–50k simulations/s, falling back to 35.9k at 64 threads — under free-threading, lock contention and memory bandwidth take over as the bottleneck; G=32 was therefore the default of that stage.
  • The per-simulation CPU ledger is emitted alongside the statistics: leaf selection 0.13–0.14 ms, inference wait 0.28–0.33 ms (stage-3 configuration) — the ratio between the two indicates where the bottleneck has shifted (CPU search vs. GPU inference).
